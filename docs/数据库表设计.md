# GuguWiki 数据库表设计

当前数据库只按 `users.role` 区分 `READER` 和 `ADMIN`。读者可以读取所有已发布文档，管理员可以管理知识库、目录、草稿和用户；不再按用户组分配知识库或文档权限。

## 当前业务表

| 表 | 主要字段 | 用途与约束 |
| --- | --- | --- |
| `users` | `id`、`email`、`display_name`、`password_hash`、`role`、`enabled`、时间戳 | 邮箱按 `lower(email)` 唯一；密码只保存哈希；角色限 `READER` / `ADMIN`。 |
| `knowledge_bases` | `id`、`name`、`description`、`icon`、时间戳 | 组织目录与文档的顶层空间；不再单独配置读者授权。 |
| `folders` | `id`、`knowledge_base_id`、`parent_id`、`title`、时间戳 | 同知识库内的目录树；复合外键保证父目录归属一致，循环关系仍由 Java 检查。 |
| `documents` | `id`、`knowledge_base_id`、`parent_id`、草稿字段、PDF 元数据、`active_version_id`、时间戳 | 管理员编辑草稿；`active_version_id` 为空表示未发布。读者只看到当前发布版本。 |
| `document_versions` | `id`、`document_id`、`version_number`、发布内容与 PDF 元数据、时间戳 | 不可变发布快照；同文档版本号唯一，生效版本只能指向本篇文档。 |

`flyway_schema_history` 由 Flyway 管理，不是业务表。数据库不存 `errorCode` 或 `error_code`；接口错误只用 HTTP 状态和 `Result.code` 表示。

## 读者可见范围

读者可访问 `documents.active_version_id` 非空的已发布内容；标题、摘要、正文和 PDF 原件以该版本为准。草稿只允许管理员查看。检索必须先限定已发布版本，再排序和截取 Top-K。具体操作还需校验登录状态、角色以及会话归属。

## SQL 文件与迁移

业务数据库只保留两份 Flyway SQL：

- [V1__create_current_tables.sql](../backend/bff/GuguWiki/src/main/resources/db/migration/V1__create_current_tables.sql)：创建当前五张业务表，每张表前都有用途注释，并建立必要的约束和索引。
- [V2__add_schema_comments.sql](../backend/bff/GuguWiki/src/main/resources/db/migration/V2__add_schema_comments.sql)：添加 PostgreSQL 表与字段注释。

新数据库直接由 Flyway 执行 V1、V2。本机数据库此前已执行旧 V1–V4，已在备份后用 Flyway `repair` 对齐 V1/V2 校验值；旧 V3/V4 的执行记录仍保留在历史表中。其他已使用旧迁移的数据库不能直接用新文件启动：须先确认旧用户组结构已经清理，再备份并修复 Flyway 记录。后续新增迁移从 V5 开始，避免与旧版本号冲突。

`infra/postgres/001_extensions.sql` 仅在新数据卷初始化时安装 `vector` 扩展，不负责业务建表。

这批迁移不会创建演示用户或保存明文密码。登录 Token 由 Java 存在 Redis 中。`document_chunks`、导入/发布任务、问答会话、评测和审计表仍需后续迁移；本文件不把尚未建成的表当作当前结构。
